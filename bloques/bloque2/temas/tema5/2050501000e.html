5. MODELO ACID Y TEOREMA DE CAP

5.1. MODELO ACID

El modelo ACID es un conjunto de principios de diseño de bases de datos para garantizar la fiabilidad y validez de los datos. Establece cuatro objetivos que cada sistema de administración de bases de datos debe esforzarse por lograr:

  • Atomicidad (Atomicity)
  • Consistencia (Consistency)
  • Aislamiento (Isolation)
  • Durabilidad (Durability)

5.1.1. ATOMICIDAD (ATOMICITY)

Atomicity establece que las modificaciones de la base de datos deben seguir una regla de "todo o nada". Se dice que cada transacción es "atómica". Si una parte de la transacción falla, la transacción completa falla. Es fundamental que el sistema de administración de la base de datos mantenga la naturaleza atómica de las transacciones a pesar de cualquier sistema de gestión de bases de datos relacionales, sistema operativo o fallo de hardware.

5.1.2. CONSISTENCIA (CONSISTENCY)

La consistencia indica que solo se escribirán datos válidos en la base de datos. Si por alguna razón, se ejecuta una transacción que viola las reglas de consistencia de la base de datos, la transacción completa se revertirá y la base de datos se restaurará a un estado consistente con esas reglas. Por otro lado, si una transacción se ejecuta con éxito, llevará la base de datos al nuevo estado consistente con las reglas.

5.1.3. AISLAMIENTO (ISOLATION)

El aislamiento requiere que las transacciones múltiples que ocurren al mismo tiempo no afecten la ejecución del otro. Por ejemplo, si Joe emite una transacción contra una base de datos al mismo tiempo que Charles emite una transacción diferente, ambas transacciones deberían operar en la base de datos de manera aislada. La base de datos debe realizar la transacción completa de Joe antes de ejecutar la de Charles o viceversa. Esto evita que la transacción de Joe lea datos intermedios producidos como un efecto secundario de parte de la transacción de Charles que eventualmente no se comprometerá con la base de datos. Ten en cuenta que la propiedad de aislamiento no garantiza qué transacción se ejecutará primero, simplemente que las transacciones no interferirán entre sí.

5.1.4. DURABILIDAD (DURABILITY)

La durabilidad asegura que cualquier transacción comprometida con la base de datos no se perderá. La durabilidad se garantiza mediante el uso de copias de seguridad de la base de datos y registros de transacciones que facilitan la restauración de transacciones comprometidas a pesar de cualquier fallo de software o hardware.

5.2. TEOREMA CAP

No todas las bases de datos cumplen con el modelo ACID. Por ejemplo, las bases de datos NoSQL no proporcionan todos los conceptos de ACID puesto que su objetivo consiste en ofrecer la máxima velocidad de respuesta asumiendo, si es necesario, alguna pérdida de datos.

Puesto que los conceptos ACID no se pueden aplicar a todos los modelos de base de datos se definió el teorema CAP (teorema de Brewer) que establece que es imposible que un almacén de datos distribuido proporcione simultáneamente más de dos de las tres garantías:

  • Consistencia (Consistency): cada lectura recibe la escritura más reciente o un error. Esto significa que todos los clientes ven los mismos datos al mismo tiempo, sin importar qué nodo se contacte. Los datos están sincronizados en todos los nodos.
  • Disponibilidad (Availability): cada solicitud recibe una respuesta (sin error), sin la garantía de que contiene la escritura más reciente. El sistema sigue funcionando incluso si algunos nodos fallan. Cada cliente puede leer y escribir, aunque algunos nodos del sistema estén caídos.
  • Tolerancia de partición (Partition Tolerance): el sistema continúa funcionando a pesar de que la red deje caer (o retrasa) un número arbitrario de mensajes entre nodos. El sistema continúa operando a pesar de las particiones de red, que pueden causar que algunos nodos no puedan comunicarse entre sí.

Es importante notar que:

  • La disponibilidad del teorema CAP entra en conflicto con la "Atomicidad" del modelo ACID.
  • La tolerancia del teorema CAP entra en conflicto con el "Aislamiento" del modelo ACID.
  • La consistencia en CAP es diferente de la consistencia en ACID. En CAP, se refiere a la consistencia de los datos en todos los nodos en un momento dado, mientras que en ACID se refiere a la integridad de los datos con respecto a las reglas definidas.

En caso de un fallo de red en tu base de datos, el teorema de CAP implica elegir entre consistencia y disponibilidad. Cuando ocurre un fallo en la red, el diseñador de la base de datos debe decidir entre:

  • CP (Consistencia y Tolerancia de partición): Cancelar la operación y, por lo tanto, disminuir la disponibilidad, pero garantizar la coherencia. Esta solución es la que se ofrece en modelos de base de datos relacional como MySQL, Oracle o SQL Server. Estos sistemas priorizan la consistencia sobre la disponibilidad en caso de una partición de red.
  • AP (Disponibilidad y Tolerancia de partición): Continuar con la operación y, por lo tanto, brindar disponibilidad pero arriesgando inconsistencia de datos. En este caso podemos pasar a utilizar un modelo NoSQL con soluciones como Cassandra o CouchDB. Estos sistemas priorizan la disponibilidad sobre la consistencia en caso de una partición de red.
  • CA (Consistencia y Disponibilidad): Algunos sistemas, como las bases de datos relacionales tradicionales que no están distribuidas, pueden ofrecer consistencia y disponibilidad, pero no tolerancia a particiones. Sin embargo, en un sistema distribuido real, las particiones son inevitables, por lo que este escenario es más teórico que práctico en sistemas distribuidos.

Es importante destacar que estas elecciones no son absolutas y muchos sistemas modernos intentan encontrar un equilibrio o ofrecer opciones configurables:

  • Consistencia eventual: Algunos sistemas NoSQL, como DynamoDB de Amazon, ofrecen una "consistencia eventual", donde el sistema garantiza que, si no se realizan nuevas actualizaciones a un objeto, eventualmente todas las acciones de acceso a ese objeto devolverán el último valor actualizado.
  • Ajustes de consistencia: Algunas bases de datos, como Cassandra, permiten ajustar el nivel de consistencia por operación, permitiendo a los desarrolladores elegir entre consistencia fuerte, consistencia eventual u opciones intermedias según las necesidades de cada operación.
  • Sistemas multi-modelo: Algunas bases de datos modernas intentan combinar las ventajas de los sistemas SQL y NoSQL, ofreciendo diferentes modelos de datos y niveles de consistencia en un solo sistema.

En resumen, el teorema CAP proporciona un marco para entender las compensaciones en el diseño de sistemas distribuidos, pero la elección entre consistencia, disponibilidad y tolerancia a particiones a menudo no es una decisión binaria, sino un espectro de opciones que dependen de los requisitos específicos de cada aplicación y caso de uso.
