3.4 PRINCIPALES PLATAFORMAS DE CONTENEDORES Y MICROSERVICIOS

Una plataforma de microservicios ofrece funcionalidades como el descubrimiento, un directorio y la monitorización de los servicios. Esto es fundamental sobre todo cuando un servicio está en mantenimiento o se escala, caso en el cual la plataforma se ocupa de comunicar la información de ubicación actualizada a todos los demás microservicios para que puedan establecer o restablecer rápidamente la comunicación.

Además, una plataforma de microservicios traslada automáticamente las instancias a máquinas virtuales o a otros servidores cuando el software o hardware en el que se ejecutan fallan o deben reiniciarse para realizar actualizaciones.

Estas son algunas de las principales plataformas más populares para desarrollar e implementar aplicaciones de microservicios:

3.4.1 DOCKER

Docker es un proyecto de código abierto que automatiza el despliegue de aplicaciones dentro de contenedores de software, proporcionando una capa adicional de abstracción y automatización de virtualización de aplicaciones en múltiples sistemas operativos.

Construido sobre las facilidades proporcionadas por el kernel Linux (principalmente cgroups y namespaces), un contenedor Docker, no requiere incluir un sistema operativo independiente. En su lugar, se basa en las funcionalidades del kernel y utiliza el aislamiento de recursos (CPU, la memoria, el bloque E/S, red, etc.) y namespaces separados para aislar la vista de una aplicación del sistema operativo. Docker accede a la virtualización del kernel Linux ya sea directamente a través de la biblioteca libcontainer (disponible desde Docker 0.9), o indirectamente a través de libvirt, LXC o systemd-nspawn.

Actualmente existe una aplicación Docker de escritorio para Windows y Mac denominada Docker Desktop.

La arquitectura de Docker se compone de tres componentes principales: el Cliente Docker, que envía comandos; el Host Docker, que ejecuta el daemon y los contenedores; y el Registro Docker, que almacena las imágenes de contenedores.

3.4.1.1 DOCKER SWARM

Docker Swarm representa el soporte integrado de Docker para administrar colecciones de motores Docker. Un Docker Swarm constituye una colección de máquinas físicas o virtuales donde se ejecuta la aplicación Docker y estas máquinas están configuradas para colaborar como un clúster. Una vez que las máquinas estén unidas como un clúster, sus comandos habituales de Docker aún se pueden usar, pero ahora serán ejecutados por las máquinas dentro del clúster. Las operaciones del clúster son supervisadas por un administrador de swarm y las máquinas que forman parte del clúster se denominan nodos.

Un Docker Swarm se refiere a una colección de máquinas físicas o virtuales que funcionan juntas como un clúster. Cuando una máquina pasa a formar parte de este clúster, asume el papel de un nodo en el Docker Swarm.

a) Nodos

El sistema Docker swarm reconoce dos tipos de nodos, cada uno de los cuales tiene responsabilidades específicas dentro del mismo:

1. Nodo administrador (manager)

Los nodos administradores manejan principalmente la asignación de tareas a los nodos trabajadores. También realizan algunas de las tareas administrativas necesarias para operar el swarm. Docker recomienda un máximo de siete nodos administradores para un swarm.

2. Nodo trabajador (worker)

En un Docker swarm con múltiples hosts, cada nodo trabajador recibe y ejecuta las tareas que le asignan los nodos administradores. De forma predeterminada, todos los nodos administradores también actúan como nodos trabajadores y pueden ejecutar tareas cuando tienen recursos disponibles.

b) Servicios y Tareas

Un servicio define las tareas que se ejecutarán en los nodos administrador o trabajador. Sirve como estructura central del sistema y es la interfaz principal para la interacción del usuario con el swarm. Al crear un servicio, los usuarios especifican la imagen del contenedor que se utilizará y los comandos que se ejecutarán dentro de los contenedores en ejecución.

Una tarea encapsula un contenedor Docker y los comandos que se ejecutarán dentro del contenedor. Es la unidad fundamental de programación dentro del swarm. Los nodos administradores asignan tareas a los nodos trabajadores según la cantidad de réplicas establecidas en la escala de servicio. Una vez que se asigna una tarea a un nodo, permanece en ese nodo y no puede moverse a otro nodo. Se ejecutará en el nodo asignado o fallará.

c) Balanceo de carga

El administrador de swarm utiliza el balanceo de carga de entrada para exponer los servicios externamente. El administrador puede asignar automáticamente al servicio un puerto publicado o los usuarios pueden configurar un puerto publicado específico para el servicio.

3.4.2 KUBERNETES

Kubernetes es un sistema de código abierto que automatiza la implementación, las operaciones y el escalado de las aplicaciones en contenedores. Originalmente desarrollado por Google, se basa en sus experiencias en servicios como Google Search y Gmail. Soporta diferentes entornos para la ejecución de contenedores, incluido Docker.

Kubernetes organiza los contenedores en unidades llamadas Pods y proporciona mecanismos para desplegar, mantener y escalar aplicaciones. Los componentes principales incluyen el API Server, Scheduler, Controller Manager y etcd en el nodo master, y Kubelet y Kube-proxy en los nodos worker.

3.4.2.1 DISEÑO

Kubernetes define un conjunto de bloques de construcción (primitivas) que conjuntamente proveen los mecanismos para el despliegue, mantenimiento y escalado de aplicaciones. Estas primitivas son las siguientes:

a) Objetos

Los Objetos de Kubernetes son entidades persistentes dentro del sistema de Kubernetes. Kubernetes utiliza estas entidades para representar el estado del clúster. Específicamente, pueden describir:

  • Qué aplicaciones corren en contenedores (y en qué nodos)
  • Los recursos disponibles para dichas aplicaciones
  • Las políticas acerca de cómo dichas aplicaciones se comportan, como las políticas de reinicio, actualización, y tolerancia a fallos

Un objeto de Kubernetes es un "registro de intención" -- una vez que se ha creado el objeto, el sistema de Kubernetes se pondrá en marcha para asegurar que el objeto existe.

Cada objeto de Kubernetes incluye dos campos como objetos anidados que determinan la configuración del objeto: el campo de objeto spec y el campo de objeto status. El campo spec, que es obligatorio, describe el estado deseado del objeto (las características que se quiere que tenga el objeto). El campo status describe el estado actual del objeto, y se suministra y actualiza directamente por el sistema de Kubernetes.

Cuando se crea un objeto en Kubernetes, se debe especificar la spec del objeto que describe su estado deseado, así como información básica del mismo (como el nombre).

Ejemplo de archivo YAML para un Deployment de Kubernetes:
apiVersion: apps/v1 # Usa apps/v1beta2 para versiones anteriores a 1.9.0
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  selector:
    matchLabels:
      app: nginx
  replicas: 2 # indica al controlador que ejecute 2 pods
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.7.9
        ports:
        - containerPort: 80

En el archivo YAML del objeto de Kubernetes obligatoriamente se tiene que indicar los valores de los siguientes campos (como mínimo):

  • apiVersion - Qué versión de la API de Kubernetes se está usando para crear este objeto
  • kind - Qué clase de objeto se quiere crear
  • metadata - Datos que permiten identificar unívocamente al objeto, incluyendo una cadena de texto para el name, UID, y opcionalmente el namespace
  • spec - Estado deseado del objeto

Todos los objetos de la API REST de Kubernetes se identifican de forma inequívoca mediante un Nombre y un UID.

Los objetos básicos de kubernetes incluyen pod, services, volumen y namespaces, que vemos a continuación.

b) Cápsulas (pod)

El objeto básico en Kubernetes se denomina cápsula o pod. Un pod consta de uno o más contenedores en los que se garantiza su ubicación en el mismo equipo anfitrión y pueden compartir recursos. Cada pod en Kubernetes es asignado a una única dirección IP que permite a las aplicaciones utilizar puertos sin riesgos de conflictos. Un pod puede definir un volumen, como puede ser un directorio de disco local o un disco de red, y exponerlo a los contenedores dentro del pod.

c) Espacios de nombre (namespaces)

Son objetos que proporcionan un mecanismo para aislar grupos de recursos dentro de un mismo cluster. Los nombres de recursos tienen que ser únicos dentro de un namespace, pero pueden coincidir en varios namespaces. Kubernetes se inicia con los siguientes namespaces:

  • Default, creado por defecto.
  • kube-node-lease: incluye los objetos de tipo lease asociados con cada nodo.
  • kube-public: puede ser leído por todos los clientes del cluster.
  • kube-system: para objetos del sistema.
d) Servicios (services)

Un servicio Kubernetes es un objeto que representa un conjunto de pods que trabajan en conjunto, como una capa de una aplicación multicapas. El conjunto de pods que constituyen un servicio está definido por el selector de etiquetas.

e) Volumenes (Volumes)

Un volumen es un directorio, que es accesible a todos los contenedores en un pod. Los archivos localizados dentro de un contenedor son efímeros, lo cual presenta problemas para aplicaciones no triviales cuando se ejecutan en contenedores. Un problema es la pérdida de archivos cuando el contenedor termina. Kubelet reinicia el contenedor con un estado limpio. Un segundo problema ocurre cuando compartimos ficheros entre contenedores corriendo juntos dentro de un Pod. La abstracción volume de Kubernetes resuelve ambos problemas.

Controladores

Además de estos objetos básicos, Kubernetes incluye objetos que son abstracciónes de nivel superior llamadas Controladores. Los Controladores se basan en los objetos básicos y proporcionan funcionalidades adicionales sobre ellos. Son controladores:

ReplicaSet

Mantiene un conjunto estable de réplicas de Pods ejecutándose en todo momento. Así, se usa en numerosas ocasiones para garantizar la disponibilidad de un número específico de Pods idénticos.

Deployment

Proporciona actualizaciones declarativas para los Pods y los ReplicaSets. Cuando se describe el estado deseado en un objeto Deployment, el controlador del Deployment se encarga de cambiar el estado actual al estado deseado de forma controlada.

StatefulSet

Gestiona pods que se basan en una especificación idéntica de contenedor. A diferencia de un Deployment, un StatefulSet mantiene una identidad asociada a sus Pods.

DaemonSet

Garantiza que todos (o algunos) de los nodos ejecuten una copia de un Pod. Conforme se añade más nodos al clúster, nuevos Pods son añadidos a los mismos. Conforme se elimina nodos del clúster, dichos Pods se destruyen.

Jobs

Un Job crea uno o más Pods y se asegura de que un número específico de ellos termina de forma satisfactoria.

Otras primitivas de Kubernetes
f) Etiquetas y selectores

Kubernetes permite a los clientes (usuarios o componentes internos) vincular pares clave-valor llamados etiquetas (en inglés label) a cualquier objeto en el sistema, como pods o nodos. El propósito de las etiquetas es permitir identificar atributos de los objetos que son relevantes y significativos para los usuarios. A través del selector de etiqueta, el cliente/usuario puede identificar un conjunto de objetos. El selector de etiqueta es la primitiva principal de agrupación en Kubernetes, y son utilizados para determinar los componentes sobre los cuales aplica una operación.

g) Anotaciones

Se pueden usar las anotaciones de Kubernetes para adjuntar metadatos arbitrarios a los objetos, de tal forma que clientes como herramientas y librerías puedan obtener fácilmente dichos metadatos.

h) Selectores de campo

Permiten seleccionar recursos basados en el valor de uno o más campos del recurso. Por ejemplo, este comando kubectl selecciona todos los Pods para los cuales el valor del campo status.phase es igual a Running:

kubectl get pods --field-selector status.phase=Running
